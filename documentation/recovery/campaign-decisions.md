# 战役与 PVE 核验记录

## 结论与边界

2026-10-20 的源数据核验覆盖了磁盘 `main` 目录中恢复的 95 个场景、423 个节点和 1,129 个触发器。其中 1,111 个为普通战斗触发器，13 个存在精英分支，18 个为章节转场触发器。这些是原始恢复统计，不包含后述本地兼容场景。

运行时目录另外加入 22 个本地兼容场景，补足 `scene/scenes` 已配置却缺少场景图的入口，因此运行时扫描总数为 117 个场景。`verify-campaign.mjs` 独立从磁盘读取 95 个源场景，再从 `ServerContent` 扫描 117 个运行时场景；创建数、代表结算和结构缺口都按 `source` / `local-runtime` 分开记录。22 个本地补建场景不计为原版恢复证据。本次运行实际创建了 1,133 个普通战斗实例和 13 个精英分支实例，156 个代表分组全部完成结算，其中 138 个来自源场景、18 个来自本地兼容场景。

新账号链路使用临时 SQLite 和本机 HTTP 服务。四个职业的初始卡组均精确为 `1, 19, 43, 61`，且都通过 101 节点。主验证账号通过公开动作首通 101、102、103、105，领取“整备卡组”“踏上征途”“主线先锋”三项正常任务经验，合法重复 105 节点 12 次达到 5 级，再首通 107 和执行章节转场，最终解锁第 2 章。全程只使用公开 HTTP 动作、合法 `battle.command` 和 `deck.save`，没有直接写数据库或伪造奖励；请求与动作精确计数保留在机器可读报告中。

## 运行时兼容决定

- 原始数据保持不变。缺失的敌人 `61152`、`65601` 和 `5901010` 分别显式映射到现存的 `60152`、`65611` 和 `590110`，战斗参数仍保留 `sourceMonsterId` 便于追溯。
- 2501、2502 和 2503 的触发器没有敌人 `param`。它们按棋盘清场模式处理：防守方没有英雄、手牌、抽牌或疲劳，初始单位正常行动；防守单位全部死亡时挑战方胜，挑战者死亡或到回合上限仍有防守单位时防守方胜。
- 源地图 12 未包含可用布局，场景 2503 引用的地图 14 同样缺布局。本次运行共有 55 个源场景战斗实例使用兼容地图；报告逐项保留源地图、有效地图和场景来源。
- 22 个缺图场景由 `scene-compatibility.mjs` 在本地内存中重建。`ServerContent.sourceSceneCount` 保留原始场景数，`runtimeSceneAdaptations` 保留每个补建场景的 provenance；磁盘恢复目录和原始场景图不改写。
- 精英参数仅在显式选择精英分支时读取，普通分支不混入 `elite` 子节点。

## 保留的源数据缺口

报告保留 8 个源数据缺口：章节 15 的两个触发器引用缺失敌人 `61152`；703 和 1903 各有一个触发器引用 `65601`；1903 的一个精英分支引用 `5901010`；2501、2502、2503 没有敌人参数。这些记录不会因运行时兼容成功而被删除。

原始场景图有 18 个不可达节点和 18 条悬空边。不可达节点均为独立副本的首个战斗节点，入边和出边都为空；运行时显式补充从场景起点到这些可选战斗节点的路由，因此 423 个已导入节点在运行时均可达。原始缺口的具体场景、节点和触发器仍保留在 `campaign-check.json`。悬空边指向没有导入的后续节点，仍是内容完整性缺口。

`scene/scenes` 有 117 条配置，其中 22 个在恢复目录中没有场景图。这 22 个入口现由可追溯的本地兼容图提供运行时路由，报告必须将它们标为 `local-runtime`，不得写成原版已恢复场景。

## 复核入口

- 执行 `npm run verify:campaign` 可重新生成核验结果。
- 机器可读证据位于 `documentation/recovery/campaign-check.json`，包含 95 个源场景与 117 个运行时场景的分层计数、本地补建 provenance、全部创建计数、代表结算结果、图结构缺口、兼容映射和 HTTP 推进证据。
- 清场模式的核心语义由 `BattleKernel.test.mjs` 的三个定向用例覆盖。
