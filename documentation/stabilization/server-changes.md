# 服务端稳定化

本轮沿用既有 Node 权威服务、SQLite、账号角色、事务、战斗和存档。原有能力不计为新增；本页列出实际补齐部分。

## 恢复与并发协议

- 每次服务启动生成 `serverInstance`。正式客户端识别重启或网络恢复，用最新权威快照建立表现基线，不无条件播放历史事件。战斗事件队列、死亡实体和嵌套动画调度沿用既有实现。
- 正式客户端将未知结果的操作先写入本地 ActionOutbox；重试沿用原 requestId、不可变内容和提交时角色 revision。新操作使用新编号，未确认的旧操作不能被另一项操作替换。账号/角色切换不应用上一角色晚到的结果。
- `expectedActorRevision` 防止同一角色两页面用旧状态提交不同操作；战斗另校验 battle revision、身份与回合。冲突返回409和可理解原因，客户端重新同步权威状态。
- 卡组使用 `expectedDeck` 比较保存基线。冲突返回当前已保存卡组，保留草稿并更新比较基线，由玩家决定再次保存。保存成功只更新已提交版本，后续编辑继续保持未保存。
- 两个预期字段为兼容旧调用方而可选；新正式客户端均发送相应字段。旧接口调用方仍受持有/组牌规则、身份、战斗 revision 与事务串行保护，但不能宣称旧调用方也具备同等乐观冲突保护。
- 网络请求15秒超时只表示结果未知，不模拟失败撤销或成功确认；原请求可继续确认。

## 事务、防重与追踪

既有 `BEGIN IMMEDIATE`、请求指纹、卡组/资产校验继续使用。新增独立 `settlements(battle_id, actor_id)` 唯一键，与资产、进度和请求回执在同一事务写入；即使热战斗记录的 settled 标志损坏，也不能再次发奖。迁移将已有结算回填到该表。

任务、邮件附件、交易等既有业务领取/完成状态仍在事务中检查。重复同请求返回原结果；相同编号不同内容409；主动新请求不能绕过业务已完成状态。新增 operation_audit 记录操作、请求、revision 和货币/卡牌/物品增减，运行日志记录 traceId 与关键操作；不记录密码、令牌或完整请求正文。

## 存档、保留与恢复

数据库 schema 1→2 在事务中迁移，可重复打开；旧账号、会话和世界数据保留。打开已有文件前只读核实数据库身份和版本，外来数据库拒绝修改。

| 内容 | 默认策略 |
|---|---|
| 完整请求回执 | 热表7天；随后 gzip 归档，至操作发生后90天仍可返回原结果 |
| 请求键与内容指纹 | 永久保留精简 tombstone；90天后原请求返回 REQUEST_EXPIRED，不重新执行 |
| 战斗奖励业务键 | 永久保留，独立于回执清理 |
| 战斗热记录 | 已结算且所有参加者都确认退出后30天归档；未确认结算不清理 |
| 经济日志 | 30天后从世界JSON移入 gzip 归档 |
| 操作审计 | 90天后移入 gzip 归档 |
| 运行日志 | 按日分文件；本轮不自动删除日志，归档保留由运维执行 |

维护为显式 CLI 操作，尚未安装后台定时任务。归档表目前不自动删除，需依据未来实际规模另定长期保留期；不能把热数据清理写成磁盘无限不增长。

```bash
node scripts/game-data.mjs metrics --database /data/tianxu.sqlite
node scripts/game-data.mjs backup --database /data/tianxu.sqlite --output /backups/snapshot-new
node scripts/game-data.mjs restore --backup /backups/snapshot-new --target /data/restored-new.sqlite
node scripts/game-data.mjs maintain --database /data/tianxu.sqlite
```

备份用 SQLite `VACUUM INTO` 生成一致快照，完整性与哈希确认后一次发布完整目录。恢复先核对哈希、完整性与版本，再原子发布到全新文件；同一未改变目标可重复确认，内容不同的已有文件禁止覆盖。先恢复到独立路径并验收，再停服务、配置新路径启动；本轮未替换个人库。回滚分支为 `codex/checkpoint-before-stabilization-20261022`，代码回退必须配合相容备份，不能以旧代码直接读新库冒充已验证回滚。

启动检测缺失前端/资源、非法端口和不可用数据库；日志记录意外异常。SIGINT/SIGTERM先停调度和HTTP，再关闭SQLite；重复停止复用同一关闭过程。

## 实际开销

测量见 storage-measurement.json。两账号、各77种持有卡的隔离夹具下，世界JSON约8.4KB，22次读取累计约2.5ms，1次写入约0.05ms；状态视图组装平均约367ms、响应约1.37MB。当前主要成本在视图组装和输出，缺乏拆分世界JSON的收益依据，本轮保持存储结构。该小样本不代表大规模并发或长期数据库性能；状态视图体积仍是后续优化项。

## 2026-10-23：地形状态接入（新增）

`BattleState.version`仍为1，新增可选`terrains`；旧状态缺字段时由内核按空数组处理，不更换数据库，也不要求清档。原有世界JSON事务天然保存地形格、拥有者、剩余回合、占用者及RNG，无需schema3。新技能解析统一在`TerrainRules.ts`与`BattleKernel.ts`，服务、AI仍复用同一内核。

地形动作沿既有出牌及requestId回执路径；重试不新增格、不额外移牌、不重跑随机。结算统一移除地形，原唯一奖励账本继续保护发奖。此次没有新增第二套服务或重写经济/存档；账号、事务、备份与防重属于已有能力，本轮只确认新状态可经过这些路径恢复。定向结果见`terrain-service-validation.md`与本轮`validation.md`。
