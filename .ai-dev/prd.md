# PRD：横屏 PVE 战术卡牌游戏

## 产品目标

将规则考证、内容设定、React 规则原型和 Cocos 视觉样板收敛为可追溯、可测试、可扩展的横屏 PVE 战术卡牌游戏。正式客户端使用 Cocos Creator 3.8.8，PC Web 首发，Android 复用同一工程；React 只作规则参考和黄金回归对照。

## 核心循环

选择职业与 30 张牌组 → 进入 PVE 关卡 → 在双路 12 格战场及双方 2×3 召唤区部署 → 自动移动、索敌、攻击和结算 → 获得卡牌、资源与任务奖励 → 调整牌组和养成 → 解锁更高 PVE 内容。

## 阶段范围

- P0 / M0–M3：工程治理、配置服务、确定性战斗核心、真实 Cocos 战斗闭环。
- P1 / M4–M6：第一章 12 节点、三段副本、挑战塔、Boss、卡牌/装备/建筑/声望/经济闭环。
- P2 / M7–M8：UI 组件化、2D 骨骼与六层场景、28 兵种、内容工具、Web/Android、账号、运营、支付、隐私与发布恢复。

## 阶段需求

- REQ-R0：Git 基线、根级质量命令、状态台账、架构拆分和 React 冻结边界完成。
- REQ-R1：配置版本/唯一 ID/引用校验、存档迁移、时间服务、原子奖励和幂等完成。
- REQ-R1A：U013–U028 的基础战斗数值、政治阵营与族属必须有可追溯设计依据，并固化为当前权威配置；政治阵营不得用族属字段替代。
- REQ-R2：Cocos 无渲染依赖的确定性核心完成；至少 24 单位、16 技能、30 能力、四职业、黄金测试和中立平衡通过。
- REQ-R2A：Cocos 必须提供可在 Node/CI 中执行的 Golden Runner；输入固定 seed 与指令流，输出终局快照、关键事件和终局哈希，重复执行结果必须一致，并能拒绝非法输入。
- REQ-R2B：Cocos 必须提供独立 Battle Runner；它根据 seed 和不含终局状态的高层战斗指令自行创建 BattleState、读取权威配置、调用 core 规则完成部署/移动/攻击/回合/胜负结算，禁止把 React 计算结果作为状态 payload 回灌。
- REQ-R2C：React 黄金对照与 Cocos Battle Runner 必须使用版本化的跨引擎对拍契约；契约明确共同 fixture、开局/准备值/回合/自动行动/round limit 的语义映射，且两侧只能从同一 seed 与高层动作流独立重建状态，不得把任一侧终局状态、事件或随机结果作为另一侧输入。
- REQ-R2C-R1：对拍修复必须统一跨引擎动作引用与单位身份，保证 round limit 的终局事件语义、版本化错误响应和 fixture 校验在两侧一致；比较必须基于双方原始终局状态与协议映射，禁止使用 outcome、哈希或另一侧输出回填缺失字段。
- REQ-R2C-R2：替代修复必须让版本化共同 fixture 的 card/unit/event mapping 被 React 与 Cocos 两端实际消费；双方独立输出并比较契约定义的原始 `finalState` 字段和协议事件语义，100 个 seed 必须覆盖部署、移动、阻挡、显式攻击、END_TURN 自动移动/索敌/攻击/胜负结算，且不得以裁剪投影、单侧终局重建或另一侧输出规避差异。
- REQ-R3：玩家可从元游戏进入真实战斗并返回；禁止用测试扣血入口代替胜负。
- REQ-R3-F1：战斗反馈投影只接受可明确定位目标的实时事件。通用目标事件必须显式给出 `targetKind` 与目标身份；`HERO_DAMAGED` 必须显式给出英雄目标身份。`side` 仅为阵营元数据，不能回退为目标身份。字段冲突、缺失、非法或结算后的事件不得改变反馈快照或核心状态。
- REQ-R4：主线、三段副本、挑战塔、Boss、奖励和养成形成可保存且不重复发放的 PVE 闭环。
- REQ-R5：UI、战斗表现、资产闸门和性能达标；24 单位/六层场景/基础特效下 PC Web ≥55 FPS、P95 ≤22ms。
- REQ-R6：Web 首发、Android 共用工程、账号/云存档、热更新、埋点、邮件、商城、合规和恢复演练通过。

## 非目标

不开发 PVP、公会、拍卖交易、实时组队、好友聊天、PVP 排行榜和独立英雄抽取；不恢复全 3D 路线；不把 React 或 Cocos Harness 宣称为正式战斗实现；Web 未稳定前不扩散 Android、支付和云服务。

## 硬约束

5 张初始手牌、12 格双路、30 张牌组配置化；主将固定且不入手牌；单位单格；规则先 ADR 再改代码；最终商业素材必须具备权利链；所有任务必须测试、回归、范围检查和独立审查。

跨引擎对拍只允许使用版本化共同 fixture 和明确字段映射；生产牌组差异、React 自动回合行为与 Cocos 显式指令行为不得通过放宽断言、复用一侧输出或修改正式规则实现来掩盖。

T114 失败后的修复只能通过新的任务重新执行；不得复用失败分支作为集成基线，不得把正式引擎事件截断、默认 deck 校验或版本错误处理当作对拍例外。
T115 失败后的替代修复必须重新创建 worktree 并由独立 reviewer 复核；T035 只有在 T116 通过 result_guard 后才可启动。

## 完成标准

M0–M8 阶段门、测试/构建/lint/性能/安全、独立审查和用户最终集成确认全部通过后，才可称为完成。历史原型通过不等于正式阶段通过。
