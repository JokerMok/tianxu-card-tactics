# 横屏战术卡牌原型系统规划自检逻辑

> 状态：历史通用自检稿。范围、战场和模块优先级以《PVE 全量复刻范围基线》和《PVE 全系统模块矩阵》为准。

版本：v0.1  
日期：2026-06-30  
用途：规划完整性检查、模块依赖检查、版本闸门检查

## 1. 自检目标

本文件用于防止系统规划遗漏关键模块、依赖倒置、过早开发商业化系统、数值系统压过核心玩法。

每次新增模块、拆版本、进入开发、改经济模型、改抽卡商城、改账号存档前，必须按本文档自检。

## 2. 总原则

- 先验证核心战斗，再扩成长。
- 先验证本地闭环，再接服务端。
- 先做免费经济，再接付费经济。
- 先有配置校验，再扩内容规模。
- 先定义数据归属，再做存档和后台。
- 先明确失败处理，再上线高价值奖励。

## 3. 完整系统分层

| 层级 | 必备模块 | 核心问题 |
|---|---|---|
| 战斗层 | 战斗核心、战斗表现、敌方 AI、战斗日志 | 一局是否好玩、可复现、可调试 |
| 构筑层 | 卡牌、牌组、英雄、技能、标签 | 玩家是否有有效策略选择 |
| 内容层 | 章节地图、关卡、Boss、活动关、引导 | 玩家是否有持续目标 |
| 成长层 | 卡牌升级、装备、天赋、玩家等级 | 玩家是否有长期成长 |
| 经济层 | 货币、材料、背包、体力、奖励 | 资源是否闭环且不失控 |
| 商业层 | 商城、抽卡、支付、订单、保底 | 付费是否可控、可查、合规 |
| 账号层 | 游客、绑定、云存档、找回、注销 | 数据是否可保存、可恢复、可删除 |
| 运营层 | 任务、活动、邮件、公告、补偿、后台 | 内容是否可持续运营 |
| 数据层 | 配置、埋点、日志、风险校验 | 问题是否可定位和修正 |
| 合规层 | 隐私、支付、抽卡概率、未成年人限制 | 是否满足上线要求 |

自检规则：任一层缺少“入口、状态、配置、奖励/消耗、日志、异常处理”，不得进入实现。

## 4. 模块生命周期自检

每个模块必须回答以下问题：

| 问题 | 通过标准 |
|---|---|
| 入口在哪里 | 玩家或系统有明确触发入口 |
| 状态存在哪里 | 本地、云端或临时战斗状态有明确归属 |
| 配置在哪里 | 有对应配置表或固定规则文档 |
| 消耗什么 | 消耗货币、体力、材料、次数或无消耗 |
| 产出什么 | 产出奖励、状态变化、记录或无产出 |
| 影响谁 | 明确影响战斗、成长、经济、账号或运营 |
| 失败怎么办 | 有失败提示、回滚、重试或降级方案 |
| 如何验收 | 有可观察结果和验收标准 |
| 如何记录 | 有日志、埋点或流水 |
| 如何关闭 | 可通过配置、版本或后台禁用 |

## 5. 依赖链自检

### 5.1 核心链路

完整产品必须满足以下主链路：

账号 -> 存档 -> 章节 -> 关卡 -> 战斗 -> 奖励 -> 背包 -> 卡牌/装备成长 -> 牌组调整 -> 新关卡。

缺失任一环节时，只能算原型，不算完整手游系统。

### 5.2 商业化链路

商业化系统必须满足：

账号 -> 商品配置 -> 支付或货币消耗 -> 订单/流水 -> 发货 -> 背包/卡牌更新 -> 日志 -> 客服可查。

缺少订单、流水、发货记录或客服查询时，不得接真实支付。

### 5.3 抽卡链路

抽卡系统必须满足：

卡池配置 -> 概率展示 -> 消耗资源 -> 生成结果 -> 保底更新 -> 重复转化 -> 背包更新 -> 抽卡记录。

缺少概率展示、保底记录或重复转化时，不得上线抽卡。

### 5.4 关卡链路

关卡系统必须满足：

章节节点 -> 解锁条件 -> 体力消耗 -> 敌方配置 -> 战斗结算 -> 星级判定 -> 奖励发放 -> 进度保存。

缺少星级、奖励或进度保存时，不得扩章节。

### 5.5 成长链路

成长系统必须满足：

材料来源 -> 升级入口 -> 消耗校验 -> 属性变化 -> 战斗生效 -> 记录变化 -> 可回溯。

缺少材料来源或战斗生效验证时，不得增加等级上限。

## 6. 版本闸门

### 6.1 Prototype 闸门

进入 Prototype 开发前必须满足：

- 核心战斗规则已定。
- 至少 20 张测试卡。
- 至少 10 个测试关卡。
- 敌方 AI 有基础策略。
- 战斗日志字段已定。
- 所有数值可配置。

Prototype 完成标准：

- 单局 5 至 8 分钟。
- 玩家每回合至少 1 个有效选择。
- 三条路线都有压力。
- 10 个关卡至少 8 个可正常完成。
- 战斗日志能定位失败原因。

### 6.2 Vertical Slice 闸门

进入 Vertical Slice 前必须满足：

- Prototype 达标。
- 第一章地图结构已定。
- 奖励系统和背包结构已定。
- 卡牌升级消耗和材料来源已定。
- 牌组编辑规则已定。

Vertical Slice 完成标准：

- 玩家可从主界面进入第一章。
- 可通关第一章。
- 可领取奖励。
- 可升级卡牌。
- 可编辑牌组并再次挑战。
- 本地存档可恢复进度。

### 6.3 Alpha 闸门

进入 Alpha 前必须满足：

- Vertical Slice 达标。
- 账号存档字段已定。
- 装备、天赋、体力系统有完整消耗产出。
- 商城和抽卡先用模拟支付。
- 抽卡概率和保底规则已定。

Alpha 完成标准：

- 账号可登录和同步。
- 装备、天赋、卡牌升级都能影响战斗。
- 商城和抽卡可完成模拟闭环。
- 经济资源不会出现无限刷取。
- 关键行为有埋点。

### 6.4 Soft Launch 闸门

进入 Soft Launch 前必须满足：

- Alpha 达标。
- 正式支付接入。
- 订单系统可查。
- 邮件和补偿可用。
- 运营后台可上下架商品和活动。
- 隐私、支付、抽卡概率展示完成。

Soft Launch 完成标准：

- 可小规模真实上线。
- 支付失败可补单。
- 玩家异常可客服查询。
- 活动可配置和关闭。
- 留存、关卡、付费数据可分析。

## 7. 经济系统自检

### 7.1 货币自检

每一种货币必须明确：

- 来源。
- 消耗。
- 日产量。
- 周产量。
- 主要消耗口。
- 溢出处理。
- 是否可付费获得。
- 是否影响战斗强度。

### 7.2 奖励自检

每个奖励包必须明确：

- 首次获得还是重复获得。
- 是否随机。
- 是否有保底。
- 是否进背包。
- 是否直接影响战斗。
- 是否可被重复领取。
- 是否有领取日志。

### 7.3 付费自检

每个付费商品必须明确：

- 商品内容。
- 价格。
- 限购。
- 展示位置。
- 解锁条件。
- 发货方式。
- 补单方式。
- 退款后的处理。

## 8. 战斗与成长平衡自检

### 8.1 战斗不被成长覆盖

以下任一情况出现，说明成长系统压过策略：

- 关卡只能靠等级碾压通过。
- 换牌组不如单纯升级有效。
- 装备属性比卡牌选择更重要。
- 天赋存在固定最优解。
- 抽到指定高稀有卡成为主线通关必要条件。

处理规则：

- 降低成长数值斜率。
- 增加关卡机制解法。
- 增加低稀有替代卡。
- 把强力卡改成构筑核心，不改成单卡通解。

### 8.2 自动推进参与感自检

以下任一情况出现，说明参与感不足：

- 玩家连续 2 回合无有效出牌。
- 玩家无法判断失败原因。
- 三条路线选择差异不明显。
- 技能卡只能补伤害，没有改变局势。
- 单局超过 8 分钟但决策次数不足。

处理规则：

- 增加低费卡比例。
- 缩短冷却。
- 增加路线特性。
- 增加控制、击退、治疗、护盾类技能。
- 优化敌方压力节奏。

## 9. 数据与配置自检

### 9.1 配置表自检

每张配置表必须满足：

- 主键唯一。
- 引用 ID 存在。
- 数值范围合法。
- 默认值明确。
- 文本 key 存在。
- 可被版本控制。
- 可回滚。

### 9.2 禁止硬编码

以下内容禁止写死在逻辑代码中：

- 卡牌数值。
- 技能参数。
- 关卡敌人。
- 掉落奖励。
- 商城价格。
- 抽卡概率。
- 保底次数。
- 任务条件。
- 活动时间。
- 功能解锁等级。

## 10. 账号与存档自检

账号系统必须回答：

- 游客账号如何生成。
- 游客账号如何绑定。
- 本地和云端冲突如何处理。
- 支付记录如何关联账号。
- 抽卡记录如何保存。
- 删除账号如何处理。
- 退款后资源如何处理。
- 多设备登录如何处理。

存档结构必须覆盖：

- 章节进度。
- 卡牌收藏。
- 牌组。
- 英雄。
- 装备。
- 天赋。
- 背包。
- 货币。
- 任务。
- 商城限购。
- 抽卡保底。
- 引导进度。
- 设置。

## 11. 运营与合规自检

### 11.1 运营自检

运营活动必须明确：

- 开始时间。
- 结束时间。
- 展示入口。
- 参与条件。
- 任务目标。
- 奖励池。
- 商店兑换。
- 未领取奖励处理。
- 活动关闭方式。

### 11.2 合规自检

上线前必须具备：

- 用户协议。
- 隐私政策。
- 第三方 SDK 清单。
- 账号注销入口。
- 数据删除入口。
- 抽卡概率展示。
- 保底规则展示。
- 充值记录。
- 订单校验。
- 恢复购买。

## 12. 缺口分级

| 级别 | 含义 | 处理 |
|---|---|---|
| Blocker | 阻止当前版本成立 | 立即补齐 |
| High | 会造成返工或数据风险 | 开发前补齐 |
| Medium | 会影响体验或运营效率 | 当前版本内补齐 |
| Low | 可后续优化 | 记录到待办 |

## 13. 当前自检结论

### 13.1 已清楚

- 产品方向：横屏 2D PVE 战术卡牌手游。
- 战斗方向：三路自动推进，玩家负责出牌和少量技能干预。
- 第一阶段：只做 Prototype，不做商城、抽卡、装备、天赋和账号服务端。
- 长期系统：已覆盖战斗、构筑、成长、内容、经济、商业、账号、运营、数据、合规。

## 14. 每次规划输出前的最终检查

输出任何新规划前，必须逐项确认：

- 是否说明目标版本。
- 是否说明该版本不做什么。
- 是否列出入口。
- 是否列出数据状态。
- 是否列出配置表。
- 是否列出消耗和产出。
- 是否列出依赖模块。
- 是否列出验收标准。
- 是否列出失败和回滚处理。
- 是否列出埋点或日志。
- 是否说明对战斗、经济、账号、运营的影响。
